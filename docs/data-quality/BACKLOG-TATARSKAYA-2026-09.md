## Порядок разбора на странице (UI / API)

Пока правила не переписаны, сортировать открытые находки так:

1. `J`, `YD` (когда появится), `Y` с кратностью ∈ {10,100,1000}±5%
2. `U` ∩ позиции с `A`/`AB` (кластер 809–819, 867–870 на этом тендере)
3. `AB`, остальные `A` с `|money_delta|` ≥ 100 тыс. ₽
4. `V`, `S`
5. `GA`, крупные `G` (одна позиция, одинаковый `parent_work_item_id`)
6. `P`, `B`, `Q`/`QA`

Код: поле `priority` или стабильная сортировка в хендлере `quality` — отдельный
тикет, не блокирует черновики SQL.

## План выката в `active`

Каждый черновик отдельно:

1. `psql` / API: замер на всей базе + на «Большой Татарской».
2. Вписать числа в «Замер» файла.
3. Сверить TP/FP из раздела «Подтверждено».
4. При включении **AB**: из SQL **A** исключить те же декады (иначе двойной список).
5. При включении **GA**: **G** либо сузить до «разные привязки», либо оставить как
   широкий warning и не дублировать одни и те же entity в обоих.
6. При включении **QA**: **Q** перевести в `draft` или оставить только материалы.
7. При включении **YD**: из **Y** исключить точные декады (Y остаётся для 11–99× и т.п.).

Пороги подбирать по дисциплине из [README](README.md): если сумма/смысл не плывут,
а число находок падает — порог верен.

## Вне SQL (код записи данных)

Не правила, но закрывают первопричину кластеров U+A:

- пересчёт привязанных материалов после смены qty работы (уже есть пайплайн —
  проверить, почему на 811/814 ГП материала живёт отдельно от формулы);

## Чего не делать
