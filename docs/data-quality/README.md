# Проверка данных тендеров — база знаний правил

Каталог правил, по которым TenderHUB ищет ошибки и нелогичности в тендерах.
Это **источник истины**: правило описано так, чтобы его мог прочитать и поправить
инженер-сметчик, а не только разработчик.

## Роли слоёв

| Слой | Где живёт | Что делает |
|---|---|---|
| **MD-правило** | [`backend/internal/quality/rules/<code>-<slug>.md`](../../backend/internal/quality/rules/) | Смысл, обоснование, подтверждённые примеры. Читают человек и LLM. |
| **SQL внутри правила** | блок ` ```sql ` в том же файле | Исполнение. Детерминированно, быстро, гоняется на каждом тендере. |
| **Вердикт инженера** | таблица `quality_acknowledgements` | Замер: «ошибка» / «принято, это норма» + причина. |
| **Разведка** | Cursor, вручную, по регламенту | Поиск **новых** классов. См. [DISCOVERY.md](DISCOVERY.md). |

> **Почему правила лежат в `backend/`, а не в `docs/`.** Их встраивает в бинарь
> `go:embed`, а он не умеет выходить за пределы своего пакета; вдобавок образ
> собирается из контекста `backend/`, куда `docs/` не попадает. Поэтому файлы правил —
> рядом с кодом, который их исполняет, а этот README остаётся точкой входа.

Нейронки в проде нет. Правила выполняет Go BFF своим пулом pgx; страница показывает
находки и собирает вердикты. LLM участвует только на этапе авторинга и разведки —
вне продакшена.

## Формат правила

Файл `rules/<code>-<slug>.md`:

```md
---
code: T
title: Сумма привязанных материалов ≠ количеству работы
severity: error | warning | info
money: yes | no
status: active | draft
entity_type: boq_item | client_position | material_name | tender
---
## Суть
Что за ошибка и почему это ошибка. Этот текст показывается инженеру на странице —
пишите так, чтобы он объяснял сам себя, без разработчика.

## SQL
```sql
-- один блок; параметр $1 = tender_id
```

## Подтверждено
- TP: <тендер, позиция, факт>
- FP: <легитимные случаи, которые правило обязано пропускать>

## Замер (дата)
Сколько находок и на какую сумму на момент замера.
```

`entity_type` — в каком пространстве лежит `entity_id`. Обязателен: по нему находка
ведёт к строке, группируется по разделам и адресуется автору правки. Если SQL
отдаёт `cp.id AS entity_id`, тип — `client_position` (это проверяет тест каталога).

### Обязательный контракт SQL

Ровно один блок ` ```sql `, ровно один параметр `$1` = `tender_id`, и строго такой
набор колонок (порядок важен — бэкенд читает по именам, но проверяет полноту):

| Колонка | Тип | Назначение |
|---|---|---|
| `tender_id` | uuid | контроль области видимости |
| `position_number` | numeric | № п/п позиции — по нему инженер находит строку |
| `item_no` | text | номер позиции заказчика (может быть NULL) |
| `entity_id` | uuid | id строки `boq_items` или `client_positions` — ключ вердикта |
| `fingerprint` | text | md5 значимых значений; **меняются данные → вердикт слетает** |
| `detail` | text | человекочитаемое описание с числами |
| `money_delta` | numeric | денежный эффект, NULL если неприменимо |

`fingerprint` — не формальность. Вердикт «принято» привязан к нему, поэтому
подтверждённая находка всплывает заново, как только значения в строке изменились.
Включайте в отпечаток ровно те поля, изменение которых должно снимать подтверждение.

## Как добавить правило

1. Заведите `rules/<code>-<slug>.md` по формату выше. Код — свободная буква/слово,
   лишь бы не конфликтовал с существующими.
2. Прогоните SQL на проде **только на чтение** и впишите результат в «Замер».
3. Найдите хотя бы один TP и, если есть, FP — без них правило нельзя регрессить.
4. Новое непроверенное правило заводится как `status: draft` — бэкенд его не выполняет,
   пока вы не переведёте в `active`.
5. Бэкенд подхватывает файл автоматически (`go:embed`), пересборка образа обязательна.

## История находок и «новое с прошлой проверки»

Каждый прогон сохраняется (`verification_runs`), а находка — как текущее состояние
(`verification_findings`, миграция `db/yandex/incremental/2026_09_verification_findings.sql`):

- находка **открывается**, когда правило выдало её впервые;
- **открывается заново**, если исчезала и вернулась или у неё сменился `fingerprint`
  (данные изменились — прежний вердикт уже не действует);
- **закрывается**, когда правило, отработавшее без ошибки, её больше не выдаёт;
- все переходы и вердикты пишутся в `verification_finding_events`.

Кнопка **«Проверка завершена»** на странице фиксирует момент: всё найденное сейчас
считается просмотренным, а «новыми» дальше помечаются только находки, открытые после
этой отметки. «Перепроверить» и автообновление страницы момент не сдвигают — иначе
признак новизны пропадал бы раньше, чем проверяющий его увидел.

Прогоны одного тендера сериализуются advisory-блокировкой (класс 42002). Если
сохранить прогон не удалось (например, миграция не применена), находки всё равно
отдаются, но без истории и признака новизны.

## Готовность по разделам ВОР

Панель на той же странице делит тендер на разделы и показывает по каждому
«Расценено» (вычисляется само) и «Проверено» (отмечает проверяющий). Миграция —
`db/yandex/incremental/2026_09_verification_sections.sql`.

- **«Расценено» ставится автоматически** по заполненности позиций, отмечать вручную
  не нужно. Позиция требует расценки, если у неё есть объём заказчика или в неё уже
  занесены строки. Такая позиция **заполнена**, если она расценена (сумма строк
  больше нуля) и указано Кол-во ГП — либо не расценена, но в «Примечании ГП» есть
  обоснование. Раздел: «расценено» — заполнены все позиции, «заполнено N из M» —
  часть, «не начато» — ни одной. Позиция без объёма и без строк — текстовая строка
  ВОР, расценки не требует.

- **Раздел** выводится из иерархии позиций: заголовок — позиция, у следующей за
  которой уровень глубже; разделом считается заголовок верхнего уровня, подразделы
  сворачиваются в него. `section_number` не используется — при загрузке ВОР он пуст.
  Позиции до первого заголовка — «Без раздела», дополнительные — отдельный раздел.
- **Отметка «проверено» заверяет содержимое**: хранится md5 позиций и строк раздела
  (`backend/internal/repository/verification_sections_sql.go`). Правка раздела
  после отметки — состояние «изменён после отметки» с числом правок строк и авторами
  из `boq_items_audit`. Пересчёт наценок и правка ссылок на источник цены отметку
  не снимают; смена курса валюты — снимает (меняются суммы).
- Отметка ставится по хешу, который видел пользователь: если раздел успели
  изменить, сервер отвечает 409 `SECTION_CHANGED`.
- Счётчики ошибок и предупреждений раздела берутся из последнего сохранённого
  прогона правил, без принятых находок и без правил в статусе `draft`.

## Сравнение с эталонами

Панель «Сравнение с эталонами» показывает по тендеру целиком, категориям затрат и
детализациям два удельных показателя и сравнивает их с эталоном. Код —
`backend/internal/analytics/costbenchmark`, справочник — миграция
`db/yandex/incremental/2026_09_benchmark_ranges.sql`, эндпоинт
`GET /api/v1/tenders/{id}/cost-benchmarks?period_months=24`.

- **₽ за единицу объёма** = коммерческая сумма категории / объём из «Затрат на
  строительство» (`construction_cost_volumes`: детализация — по id, категория — группа
  `category-<имя>`). Без объёма показатель не считается.
- **₽ за м² по СП** = коммерческая сумма / `tenders.area_sp`. Итог тендера — сумма строк
  без страхования, чтобы объекты с разными настройками страхования были сопоставимы.
- **Эталон** выбирается так: ручной диапазон из справочника (самый конкретный: класс и
  объём строительства → класс → объём → любой объект), иначе статистика согласованных
  тендеров своего класса, иначе всех классов. Для статистики нужно не меньше 5 тендеров,
  выбросы — по Тьюки; отбор истории тот же, что у ценовых отклонений (согласован, расчёт
  актуален, последняя версия номера), другие версии самого тендера не учитываются.
- Если ручной диапазон есть, а медиана истории своего класса лежит вне его, строка
  помечается «справочник расходится с историей» — ориентир мог устареть.
- Коммерческие суммы материализуются пересчётом, поэтому пока расчёт тендера не
  актуален, сравнение не выдаётся.
- Справочник видят все, правят роли `administrator`, `developer`, `director`,
  `general_director`, `veduschiy_inzhener`. Удаление мягкое.

## Дисциплина порогов

Порог — часть правила, а не деталь реализации, и он подбирается **по замеру, а не на
глаз**. Показательный пример — правило **I**: допуск ≥ 1 ₽ даёт 2 568 находок,
допуск ≥ 100 ₽ — 621 находку, **при одной и той же сумме расхождений (−106.3 млн ₽)**.
То есть 1 947 находок были шумом, за которым нет денег. Без допуска вообще правило
выдаёт 28 737 строк, из них 26 169 — арифметика с плавающей точкой.

Правило: подняли порог — **перезамерьте и покрытие, и число находок**. Если сумма не
изменилась, а находок стало меньше, порог поднят правильно. Если поехала сумма —
вернитесь назад. Если правило шумит, порог ужимается и замер переснимается.

Точность правила считается из вердиктов: `ошибки / (ошибки + принято)`. Ниже ~50% —
правило шумит: ужимайте порог, добавляйте исключения или переводите в `draft`.

должно появиться, чтобы правило вернулось.

Нужна семантика наименований |

### Черновики конвейера проверки (ждут замера)

Заведены под ручные шаги проверки расчёта: «количество ГП во всех расценённых
строках», «обоснование во всех пустых строках», «нерасценённые строки, которые
упустили». Не выполняются, пока не снят замер на проде.

SQL каждого проверен на схеме из `db/yandex/sql/` и на синтетической фикстуре:
правило срабатывает ровно на целевой позиции и молчит на соседних, специально
сконструированных как отрицательный случай. Это не заменяет замер — он показывает
объём находок и точность, которых на фикстуре не видно.

| Код | Правило | Severity | Что закрывает |
|---|---|---|---|
| [U](../../backend/internal/quality/rules/U-position-priced-no-gp.md) | Позиция расценена, но Кол-во ГП не задано | error | ГП во всех расценённых строках |
| [V](../../backend/internal/quality/rules/V-empty-position-no-reason.md) | Конечная позиция не расценена и без обоснования | error | обоснование во всех пустых строках |
| [W](../../backend/internal/quality/rules/W-unpriced-in-priced-section.md) | Нерасценённая позиция внутри расценённого раздела | warning | строки, которые упустили |
| [X](../../backend/internal/quality/rules/X-gp-equals-client-volume.md) | Кол-во ГП в точности равно количеству заказчика | warning | объём не пересчитывали |
| [Y](../../backend/internal/quality/rules/Y-gp-volume-order-mismatch.md) | Кол-во ГП расходится с заказчиком более чем в 10 раз | warning | опечатка на порядок |
| [Z](../../backend/internal/quality/rules/Z-gp-volume-without-unit.md) | Кол-во ГП задано, единица измерения пуста | warning | удельные показатели неинтерпретируемы |
| [AA](../../backend/internal/quality/rules/AA-position-without-cost-category.md) | В позиции ни у одной строки нет категории затрат | warning | позиция невидима в разрезе затрат |

**Порядок активации важен.** Правила **H** и **U** сейчас пересекаются: H ловит
любую позицию со строками при нулевом ГП, U — только ту, где уже есть деньги.
Сужать H (`HAVING SUM(total_amount) = 0`) можно **только одновременно** с
переводом U в `active`, иначе расценённые позиции без ГП на время выпадут из
проверки вообще. Оба правила после этого перезамеряются.
