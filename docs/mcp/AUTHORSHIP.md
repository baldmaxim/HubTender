# Авторство и подтверждение записей MCP

С 16.10.2026. Правила действуют только для записи через MCP. Портал работает как
раньше: инженеры и старшие правят любые строки, как и до выкладки.

## Чьи данные можно менять через MCP

Агент работает под учёткой пользователя TenderHUB (OAuth), поэтому автор каждой
записи известен.

| Действие через MCP | Можно |
|---|---|
| Добавить строку `суб-раб`/`суб-мат` в конечную позицию | всегда (проверки + подтверждение) |
| Изменить строку (цена, количество, перевод) | только «свою» строку |
| Изменить количество работы | работа и все её привязанные материалы — «свои» |
| Изменить только цену работы | своя работа; привязанные материалы не меняются |
| Удалить строку (`tenderhub_delete_boq_item`) | своя строка; у работы — и все привязанные материалы |
| Заполнить пустое количество/примечание ГП | всегда |
| Изменить заполненное количество/примечание ГП | только если последним его менял этот же пользователь |

«Своя» строка — последнее изменение строки сделано под учёткой этого
пользователя: добавление или правка входных полей. Автором **не** делают
пересчёты: итог строки (`total_amount`), коммерция, порядок строк, количество
привязанного материала от его работы. Строка без автора под учёткой
(«Системная операция») для MCP только на чтение.

Отказ возвращается как `MCP_NOT_AUTHOR` с ФИО последнего автора; такую строку
правят в портале или просит автор.

Автор берётся из аудита ВОР: `public.boq_item_last_authorship(item)`. ГП — из
журнала `public.client_position_gp_audit`:
`public.client_position_gp_last_authorship(position, 'volume'|'note')`.

## Перенос авторов в новую версию

«Новая версия» (`clone_tender_as_new_version`) и перенос при сопоставлении строк
заказчика (`ExecuteVersionTransfer`) пишут для каждой скопированной строки одну
запись аудита: автор и время его последнего изменения в предыдущей версии,
`changed_fields = {version_copy}`. В истории изменений позиции она видна как
«Перенос версии». Тот, кто создаёт версию или переносит, автором чужих строк не
становится. Так же переносится журнал ГП (`origin = version_copy`).

Полная история строки остаётся у строки предыдущей версии; копируется только
последний автор, иначе аудит рос бы на весь объём тендера при каждой версии.

Версии, созданные до выкладки, автора не получили: их скопированные строки для
MCP без автора. Восстановление по предыдущей версии — отдельный шаг после
выкладки (сначала отчёт).

## Журнал ГП

`public.client_position_gp_audit`: кто, когда, было → стало для количества и
примечания ГП; для MCP — `request_key`. Пишет триггер
`trg_client_positions_gp_audit` при любом изменении (портал, импорт, отмена
импорта, MCP); пользователь — из `app.user_id` транзакции. Кто ставил ГП до
выкладки, не записано: такие значения для MCP без автора.

## Окно подтверждения

Каждая запись MCP показывает человеку окно в клиенте (MCP elicitation): тендер,
позиция, раздел, строки «было → стало» или удаляемые, автор строки, ГП, итог
позиции, замечания проверок. Подтвердить может только человек: аргументов
«подтверждено» у инструментов нет. Клиент без окна получает
`MCP_CONFIRMATION_UNSUPPORTED` и писать не может, в том числе автоматические
агенты без человека.

Ответ привязан к показанному тексту и данным: если между показом и записью
что-то изменилось — `MCP_CONFIRMATION_STALE`, нужно повторить запрос.

Как окно доходит до клиента:

- протокол `2026-07-28` и новее — окно в ответе инструмента (multi round-trip,
  SEP-2322), клиент повторяет вызов с ответом;
- старые версии (Cursor на момент выкладки) — сервер присылает
  `elicitation/create` посреди вызова по SSE. Для этого MCP работает с сессиями
  (`Mcp-Session-Id`, 30 минут простоя); сессию может продолжить только тот же
  пользователь. Ответ в окне — в пределах таймаута запроса (5 минут).

`MCP_STATELESS_HTTP=true` — аварийный режим без сессий: окно работает только у
клиентов с протоколом `2026-07-28`, остальные писать не могут.

nginx для `/mcp` должен пропускать SSE без буферизации: `proxy_buffering off`,
`proxy_read_timeout` не меньше 300 секунд (`deploy/nginx-mcp.conf.example`).
