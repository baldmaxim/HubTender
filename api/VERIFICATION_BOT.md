# Telegram-бот рассылки замечаний «Проверки данных»

API для бота, который доставляет исполнителям замечания проверки расчёта и принимает их
ответы кнопками. Бот работает на офисном ПК (программа `bots/verification-bot/`) и сам ничего
не решает — это тонкий ретранслятор между Telegram и TenderHUB:
- очередь сообщений, выбор адресатов, тексты и кнопки — на сервере;
- привязка Telegram к пользователю, команда `/stop` и вердикты по кнопкам — тоже на сервере;
- бот опрашивает Telegram (`getUpdates`), пересылает обновления в API и выполняет то, что
  API вернул.

Токен бота живёт только на ПК, сервер в Telegram не ходит.

Рассылку ставит в очередь проверяющий кнопкой «Отправить исполнителям» на странице «Проверка
данных» (только из интерфейса, по ключу это недоступно). Бот эту очередь только забирает.

Base URL: `https://gp.su10.ru`. Все пути ниже начинаются с `/api/v1`. Ответы приходят в
конверте `{"data": …}`. Ошибки — RFC 7807 с полем `code`.

## Ключ

Ключ выпускает администратор: «Администрирование → Доступ к API → Выпустить ключ».
- Название — например, «Бот рассылки замечаний (офисный ПК)».
- Права: **«Telegram-бот рассылки замечаний»** (`verification:telegram`).
- Список тендеров **не задавать**: бот рассылает замечания по всем тендерам, ограниченный
  ключ получит `403 API_KEY_TENDER_DENIED`.
- Срок действия — по желанию.

Передавать ключ в заголовке `X-API-Key: thk_…`, **не** в `Authorization: Bearer`.
Маршруты открыты только по ключу: пользователь с обычной сессией портала получит
`403 API_KEY_REQUIRED`.

## Готовое сообщение `message`

Поле `message` — параметры метода Bot API `sendMessage` без `chat_id`
(`text` в HTML, `parse_mode: "HTML"`, при наличии кнопок `reply_markup`). Отправка:
`sendMessage({chat_id, ...message})`. Текст уже экранирован и умещается в лимит Telegram.

Кнопки под замечаниями несут `callback_data` вида `a:<uuid>` («норма») и `e:<uuid>`
(«ошибка, исправлю»). Бот не разбирает их, а пересылает как есть в `updates`.

## Эндпоинты

### `POST /verification-bot/updates` — обновление Telegram

Тело — **одно** обновление из `getUpdates`, как пришло от Telegram, в поле `update`:

```json
{"update": {"update_id": 501, "message": {"message_id": 9, "date": 1792670400,
  "chat": {"id": 123456789, "type": "private"}, "from": {"id": 123456789, "username": "ivan"},
  "text": "/start Zm9vYmFy"}}}
```

Ответ — действия, которые боту надо выполнить по порядку (список может быть пустым):

```json
{"data": {"actions": [
  {"method": "sendMessage", "chat_id": 123456789,
   "message": {"text": "Готово, Иванов Иван. Сюда будут приходить замечания …", "parse_mode": "HTML"}},
  {"method": "answerCallbackQuery", "callback_query_id": "8472…", "text": "Отмечено: норма"}
]}}
```

| `method` | Что сделать |
|---|---|
| `sendMessage` | `sendMessage({chat_id, ...message})` |
| `answerCallbackQuery` | `answerCallbackQuery({callback_query_id, text})` — закрыть «часики» на кнопке |

Что обрабатывается:
- `/start <токен>` в личном чате — привязка Telegram к пользователю TenderHUB;
- `/stop` — отвязка и отключение уведомлений;
- кнопки «норма» / «ошибка» под сообщением — вердикт по замечанию;
- любой другой текст — подсказка. Групповые чаты и прочие обновления игнорируются
  (`actions: []`).

Бот шлёт в API **каждое** обновление, не фильтруя. `offset` в Telegram продвигайте только
после ответа `200`. Ответ `5xx` — внутренняя ошибка сервера: повторите то же обновление позже,
повтор безопасен (привязка и вердикт идемпотентны).

### `POST /verification-bot/claim` — очередь сообщений

Тело: `{"bot_username": "SU10_Checks_bot", "limit": 20}`.
- `bot_username` — имя бота без «@», 5–32 символа (латиница, цифры, `_`). По нему сервер
  собирает ссылку привязки `https://t.me/<имя>?start=<токен>`.
- `limit` — сколько сообщений отдать: по умолчанию 20, максимум 50.

```json
{"data": {"messages": [
  {"id": "0f8fad5b-d9cb-469f-a165-70867728950e", "chat_id": 123456789,
   "message": {"text": "<b>Замечания по расчёту</b> …", "parse_mode": "HTML",
               "reply_markup": {"inline_keyboard": [[…]]}}}
]}}
```

- Вызов одновременно говорит серверу «бот в сети».
- Выданное сообщение берётся **в аренду на 2 минуты**: пока итог не пришёл (или аренда не
  истекла), второй раз оно не выдаётся. Не прислали итог — сообщение вернётся в очередь.
- Сообщения, которые отправлять не нужно (адресат отвязал Telegram, находки уже исправлены),
  сервер закрывает сам и не выдаёт.
- `messages` всегда массив.

### `POST /verification-bot/notifications/{id}/result` — итог отправки

`{id}` — `messages[].id`. Тело — результат `sendMessage`:

```json
{"ok": true, "message_id": 7231}
{"ok": false, "error_code": 403, "description": "Forbidden: bot was blocked by the user"}
{"ok": false, "error_code": 429, "description": "Too Many Requests: retry after 17", "retry_after": 17}
{"ok": false, "error_code": 0, "description": "timeout"}
```

| Поле | Значение |
|---|---|
| `ok` | сообщение доставлено |
| `message_id` | id отправленного сообщения (при `ok`) |
| `error_code` | код ошибки Telegram; `0` — сетевая ошибка, ответа Telegram не было |
| `description` | описание ошибки (хранится в журнале сообщения, до 300 символов) |
| `retry_after` | секунды из `parameters.retry_after` ответа `429` |

Ответ: `{"data": {"status": "sent" | "failed" | "pending" | "skipped"}}`.
- `sent` — доставлено;
- `failed` — повтор не поможет (`400`/`403`: бот заблокирован, чат не найден) или исчерпаны
  попытки (5);
- `pending` — сообщение вернётся в очередь: через `retry_after` секунд, а без него — с
  нарастающей паузой (2, 4, 8 … минут). Следующий `claim` выдаст его снова;
- `skipped` — сообщение закрыто сервером раньше.

Итог по уже закрытому сообщению ничего не меняет и возвращает его текущий статус — повтор
запроса после сетевой ошибки безопасен. Нет такого сообщения — `404 VERIFICATION_BOT_NOT_FOUND`.

## Цикл работы бота

1. **Обновления.** Бесконечный цикл `getUpdates` (long polling, `allowed_updates`:
   `message`, `callback_query`). Для каждого обновления — `POST /verification-bot/updates`,
   затем выполнить `actions` по порядку. После успешного ответа сдвинуть `offset`.
2. **Очередь.** Раз в 30 секунд — `POST /verification-bot/claim`. Каждое сообщение из
   `messages` отправить `sendMessage({chat_id, ...message})` и сразу сообщить итог через
   `…/notifications/{id}/result`. Между сообщениями — пауза не меньше 1 секунды (личные
   чаты; общий лимит Telegram — около 30 сообщений в секунду, но один чат — 1 в секунду).
3. **Ошибки Telegram.** Передавать `error_code`, `description` и `retry_after` как есть:
   решение, повторять ли, принимает сервер.

«Бот в сети» в интерфейсе — это `claim` за последние 90 секунд. Раз в 30 секунд бот этого
срока не пропускает, но если ПК выключен, интерфейс показывает «бот не в сети».

## Если ПК выключен

- Очередь ждёт: сообщения остаются `pending` и уходят при первом `claim` после запуска бота.
- `Start`, нажатый пользователем в течение 15 минут жизни ссылки, засчитывается и позже:
  срок токена проверяется по времени сообщения (`message.date`), а не по времени, когда бот
  переслал обновление. Telegram хранит необработанные обновления до суток, поэтому
  засчитывается Start не старше 24 часов.
- Старые кнопки: вердикт по замечанию ставится, даже если нажали давно (если строка не
  изменилась). Но Telegram даёт отвечать на нажатие только короткое время, поэтому
  `answerCallbackQuery` после долгого простоя может не показаться — это не влияет на
  результат, вердикт уже сохранён.

## Ошибки

| HTTP | `code` | Что значит |
|---|---|---|
| 401 | — | ключ не передан, неверен, отозван или истёк |
| 403 | `API_KEY_REQUIRED` | запрос пришёл не по ключу (сессия портала) |
| 403 | `API_KEY_SCOPE_DENIED` | у ключа нет области `verification:telegram` |
| 403 | `API_KEY_TENDER_DENIED` | ключ ограничен списком тендеров — для бота так нельзя |
| 400 | `VERIFICATION_BOT_INVALID_REQUEST` | неверный запрос (нет `update`, плохое `bot_username`, не uuid в `{id}`); причина — в `detail`. Тело — JSON-объект не больше 64 КБ |
| 404 | `VERIFICATION_BOT_NOT_FOUND` | сообщения нет в очереди |
| 429 | — | превышен лимит вызовов ключа в минуту |
| 500 | — | внутренняя ошибка сервера: повторить запрос позже |

Все вызовы видны в журнале: «Администрирование → Доступ к API».

## Проверка связи

```bash
KEY=thk_…   # не оставляйте ключ в истории оболочки
curl -s -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"bot_username": "SU10_Checks_bot", "limit": 1}' \
  https://gp.su10.ru/api/v1/verification-bot/claim
```

Внимание: `claim` выдаёт сообщения в аренду. Если в очереди что-то есть, проверочный вызов
«займёт» сообщение на 2 минуты, пока настоящий бот не пришлёт итог.
